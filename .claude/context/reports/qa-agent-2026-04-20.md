## KRITIK BULGULAR

### 1. Stripe Webhook Idempotency Yok — Duplicate Event Riski

- **Dosya**: `packages/api/src/modules/billing/router.ts:207-342`
- **Akis**: Stripe -> `/hooks/stripe` -> `constructWebhookEvent` -> switch(event.type)
- **Senaryo**: Stripe ayni `event.id`'yi retry ederse (network hata, timeout), hic bir idempotency kontrolu yok. Ornek:
  - `customer.subscription.updated` ayni eventId ile 2 kere gelir -> `prisma.tenant.update` 2 kere calisir (idempotent ama ActivityLog duplicate).
  - `checkout.session.completed` iki kere -> `stripeSubscriptionId` ayni deger (OK) ama referral bonus veya plan upgrade 2 kere tetiklenebilir (mevcut kodda degil ama gelecek risk).
- **Beklenen**: `webhook_events` tablosu (yok) veya Redis SETNX ile `event.id` kaydedilip, duplicate ise early-return.
- **Onem**: Yuksek — production'da Stripe resmi dokumaninda retry edebilecegi belirtiliyor.
- **Cozum**:
  ```typescript
  // En basta
  const seen = await redis.set(`stripe:evt:${event.id}`, "1", "NX", "EX", 86400 * 7);
  if (!seen) { logger.info({id: event.id}, "Duplicate stripe webhook — skipped"); res.json({received: true, duplicate: true}); return; }
  ```

### 3. Stripe Webhook Route Mount Hatasi — Raw Body Limiti

- **Dosya**: `packages/api/src/index.ts:77, 137`
- **Sorun**: Global `app.use(express.json({ limit: "10mb" }))` `app.listen`'den oncesi. Ancak `stripeWebhookRouter` kendi `raw({ type: "application/json" })` kullaniyor (router.ts:209). Express route sirasinda, global JSON parser zaten calismis olabilir bazi transport durumlarda — ama router `raw` body parser'i kendi scope'unda. Ek bir test lazim: **`/hooks/stripe`'a gerceken raw body gelir mi?**
- **Risk**: Eger global JSON parser once calisirsa `req.body` JSON parsed olur ve imza dogrulamasi her zaman patlar -> 400 donecegi icin fark edilir, ama production'da tum webhookler fail olabilir.
- **Dogrulama**: Stripe test gondermesi ile imza dogrulamanin gectiği manuel test gereklidir — integration test yok.

### 4. Run Execution — Infinite Loop / Uzun Suren Run Icin Wall-Clock Timeout Yok

- **Dosya**: `packages/api/src/modules/pipeline/runner.ts:32-327`
- **Sorun**: `processRun` icinde step'lere tek tek girilir. Her step icinde `runAgentLoop` (`claude.ts:310-312`) `maxTurns: 10` ve `budgetUsd: 1` ile calisir, fakat **global run wall-clock timeout yoktur**.
  - Senaryo A: Agent sonsuz dongude tool-call yapmaz ama API 60 saniye cevap vermez -> BullMQ worker `timeout` yok, sureli kilitlenir.
  - Senaryo B: Loop detection sadece ardisik 5 FAILED step'te (`governance/engine.ts:130-146`). Eger tum step'ler COMPLETED ama surekli tool call yapiyor (budget kontrol var ama N step sonra tekrar budget sifirlanir), loop devam eder.
  - Senaryo C: `runQueue.add(... { attempts: 1 })` (runner.ts:337) — retry yok, ama wedged job concurrency'yi tuketir.
- **Onem**: Yuksek — V1 free plan 10 run/ay limitli, bir tane wedged run tum quota'yi yakabilir.
- **Cozum**:
  - BullMQ job timeout: `await runQueue.add(... { jobId, attempts: 1, removeOnComplete: {count:100}, timeout: 15 * 60 * 1000 })` (15 dk hard cap)
  - `setTimeout` ile soft cap ve `prisma.run.update({status: "FAILED", error: "Timeout"})`
  - Toplam step sayisi (`allSteps.length`) >50 -> reject

### 5. Quota Enforcement — Race Condition (TOCTOU)

- **Dosya**: `packages/api/src/modules/billing/metering.ts:69-110` + `packages/api/src/modules/pipeline/runner.ts:58-83`
- **Akis**:
  1. `pipelineRouter.post("/:id/run")` -> `prisma.run.create` -> `enqueueRun` (router.ts:213-234). **Quota check yok** burada.
  2. BullMQ worker icinde `checkQuota` yapilir ve gecerse `incrementMeter(tenantId, "runs", 1)`.
- **Race**: Ayni anda 2 istek gelir, ikisi de PENDING olarak DB'ye yazilir, sonra worker once birini alir. `checkQuota` read-then-write atomik degil — ayni anda iki worker, her ikisi de "9 < 10 OK" der, sonra ikisi de increment. Gercek value 11'e cikar. Sadece sonraki run icin engelleme olur.
- **Ek sorun**: `checkQuota` sadece `"runs"` metric'i icin calisir, ama `incrementMeter` metering.ts:53'te `metric === "runs" ? limits.maxRunsPerMonth : -1`. `tool_calls` icin limit -1 (unlimited) ama Free plan'da tool call sinirlanmali.
- **Cozum**: Atomik `INCR + check` pattern. Prisma raw: `UPDATE usage_meters SET value = value + 1 WHERE tenant_id=... AND value < $limit RETURNING value` — eger 0 row donerse reject. Veya Redis ile pre-check.
- **Bypass**: Frontend (billing/page.tsx) plan'i gorur ama quota check butun backend'te — yine de `/pipelines/:id/run` endpoint'i pre-check yapmiyor. Kullanici UI'i bypass edip direkt API'ye 100 request gonderebilir, hepsi enqueue olur, BullMQ sirali islerken meter overshoot eder.

### 6. Draft.approve — Email Gonderim Hatasi Sessiz Yutuluyor
